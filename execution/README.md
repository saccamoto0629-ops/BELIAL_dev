## Safety Gate / 送信サービスの境界

- Strategy は Safety Gate の判定を持たない。Broker Adapter は Safety Gate のポリシーを持たない。raw Broker は型付き `BrokerConnection` としてサービスへ注入され、外へ公開されない。
- `LiveOrderSubmissionService.submit()` は「意図復元 → 評価 → 判定の耐久保存 + read-back → Submission Journal 記録(Issue #93)→ created→submitting 遷移獲得 → Journal started 更新」に**すべて成功した呼び出しだけ**が `ExecutionRequest.to_order_request()` と `Broker.submit_order()` に到達する。
- 1 件でも違反・kill switch 有効・Broker / store 照会失敗・判定保存 / read-back 失敗・**Journal 保存失敗**・二重送信・UNKNOWN 後の再送・想定外例外は fail-closed で送信しない。
- **kill switch は永続かつ fail-closed**(Issue #81): production の状態源は `kill_switch_store.py` の SQLite(`PersistentKillSwitchStateProvider`)であり、有効化はプロセス再起動・サービス再構築・別プロセスをまたいで新規送信を停止し続ける。store が読めない(未初期化・schema 不一致・破損)あいだも `state_query_failed` で全新規送信が拒否される。reconciliation・read-only 照会・cancel 経路は Gate を通らないため停止中も実行できる。操作は `kill_switch_cli.py`(解除は明示 `--confirm-resume` 必須)。
- `BrokerConnection` の mode / target は Broker 自身の `connection_identity()`(構築時 config 由来・不変)から**導出**され、mode は具象型と相互検証される: `fake` = FakeBroker のみ、`demo` / `live` は Adapter 型が登録されるまで**構築不能**。
- 迂回は「呼び出し側の注意」ではなく **AST 走査テスト**(`tests/test_submission_boundary.py`)で構造的に禁止する: `submit_order` / `to_order_request` の呼び出し箇所は公認箇所以外に存在できない。この境界は**誤用防止**であり、reflection 等による**故意回避の in-process 防止は言語的に不可能**(実 Adapter 導入時の運用境界で扱う。[設計書の該当節](../docs/architecture/safety_gate.md)参照)。
- FakeBroker の `submitted_requests` により、全拒否経路で Broker 送信がゼロ件であることをテストする。

## execution mode(dry-run / shadow / fake / demo / live)

mode の唯一の正は `execution.safety_gate.ExecutionMode`。設定文字列は `resolve_execution_mode()` がロード時に解決し、**未知の mode は起動時に明示拒否**する。

- `dry-run`: 副作用ゼロ(Broker 呼び出し・DB 作成・migration・INSERT/UPDATE・state 更新・Discord いずれもなし。既存 DB は read-only probe のみ)。
- `shadow`: 実 Signal・実設定・Safety Gate を通常経路で実行し、**Broker へは送信せず**検証記録を保存する(下記)。仮想約定・仮想 Position・仮想 PnL は計算しない(それは Paper Execution の責務)。
- `fake`: FakeBroker へ送信(`LiveOrderSubmissionService` 経由。既存の注文状態機械・保存を使用)。
- `demo` / `live`: **mode 定義と validation のみ。Execution 層への組み込みは未実装**。OANDA Demo Adapter 自体は Issue #79 で `broker/oanda_demo_adapter.py` に実装済みだが、`BROKER_TYPE_BY_MODE` に Adapter 型が登録されるまで `BrokerConnection` を構築できず、runner は明示的に拒否する(登録は別 Issue)。

## Shadow Mode(Issue #78 / PR #100)

Demo / Live 接続前に実際の判定経路を検証するための監査記録機能。**「実 Signal を利用する」経路は保存済み Signal を読む Production 経路**(`--signal-id` / `run_production_shadow_cycle`)であり、CLI JSON は `cli_fixture` として明確に区別される。`ShadowExecutionService` は「**claim(Gate 評価前の identity 確保)** → `SafetyGate.evaluate_shadow()` → 判定の耐久保存 + read-back → complete」を実施する。**Broker API は一度も呼ばれない**(サービスに Broker を渡す引数が存在しない。全 Broker API を毒化した pytest と `broker_submit_calls: 0` の固定シナリオで回帰固定)。Gate 拒否でも Shadow 記録は保存される。

- 保存先は専用 DB `data/shadow_results.sqlite3`(`SHADOW_RESULT_DB_PATH`)。**通常注文状態とは別 namespace**: Shadow は `execution_orders` に登録せず、**将来の fake / demo / live 送信をブロックしない**。
- **claim-first idempotency**: loser は Gate を評価せず decision も書かないため **completed 1 件 : Safety Decision 1 件**。同一 payload の再実行・並行実行は明示 duplicate、**payload が 1 項目でも異なれば `ShadowIdentityConflictError`**(既存結果を黙って返さない)。claim の所有単位は run_cycle 1 回ごとの attempt(`claim_attempt_id` + fencing token `claim_generation`)で、**有効期限内の claim は同一 service / 同一 owner でも再取得できない** — crash や完了失敗で残った claim は lease 切れ後の takeover(generation +1)でのみ回収され、旧 attempt の complete は fencing 不一致で明示失敗する(orphan decision は `shadow_report --orphan-decisions` で追跡)。DB lock エラーは duplicate に化けない。
- Gate のポジション / 口座上限は注入 snapshot(`AccountSafetySnapshot`)から評価され(live と同一の鮮度・型検証)、**snapshot 全体が監査保存される**(拒否の事後再現が可能)。

```bash
# Production Signal 経路(保存済み Signal + Production 設定。default なし)
python -m execution.shadow_runner --mode shadow --signal-id <signal_id> \
  --signal-db paper-signal/data/paper_signals.sqlite3 \
  --execution-config <config.json> --market-snapshot <market.json> --account-snapshot <account.json>
# CLI fixture 経路(input_origin=cli_fixture として記録)
python -m execution.shadow_runner --mode shadow --cycle execution/examples/shadow_cycle_example.json --data-dir /tmp/shadow
python -m execution.shadow_runner --mode dry-run --cycle ...        # 完全無副作用(true read-only probe)
python -m execution.shadow_report --shadow-db /tmp/shadow/shadow_results.sqlite3 [--limit 20]
python -m execution.shadow_report --shadow-db ... --execution-request-id <id> | --safety-decision-id <n>
python -m execution.shadow_report --shadow-db ... --claims | --orphan-decisions | --decision rejected --json
```

設計の詳細(provenance / claim / lease / duplicate と conflict / decision 1:1 / account snapshot / true read-only / JSON 入力制限)は [docs/architecture/shadow_execution.md](../docs/architecture/shadow_execution.md) を参照。

## Broker Reconciliation(Issue #103 / #104)

内部注文状態と Broker 注文状態を照合し、不一致を分類・記録する**検出**基盤(Issue #103)と、`auto_repair_candidate` に分類された注文状態だけを既存状態機械経由で内部へ冪等に反映する**修復サービス**(Issue #104)。検出は**内部注文状態を変更せず**、修復は**内部 DB のみ**を更新する。**どちらも Broker へ注文を送信・キャンセルしない**(Broker は照会系 `get_order` / `list_orders` のみ)。

```python
service = BrokerOrderReconciliationService(
    broker=broker, execution_db_path=..., reconciliation_db_path=...)
run = service.run(run_id="recon-...")     # 検出 + ログ + DB append
run = service.detect(run_id="recon-...")  # 検出 + ログのみ(DB を作らない)

repairer = BrokerOrderReconciliationRepairService(
    broker=broker, execution_db_path=..., reconciliation_db_path=...,
    owner_id="repair-worker-1", lease_duration_seconds=600)   # broker timeout < lease を構築時に検証
result = repairer.repair(run_id="recon-...")                          # claim → fenced 適用 + 監査 append
result = repairer.repair(run_id="recon-...", mode=RepairMode.DRY_RUN)  # 評価のみ(無副作用)
recovered = repairer.recover_pending_attempts()                        # lease 切れ pending の takeover
```

- 検出する差分: 内部発注中 × Broker FILLED / CANCELLED / REJECTED、内部 UNKNOWN × Broker 確定、終端状態同士の矛盾、Broker 側のみの注文、Broker が知らない注文、その他の不一致、照会失敗。**状態・注文 identity・snapshot 契約がすべて一致する場合のみ差分としない**。終端状態も外部事実との矛盾検出のため照合し、`created` intent のみ除外する。
- 分類: `auto_repair_candidate`(既存状態機械・store 契約で情報を失わず反映できる)/ `manual_review`(他注文が所有する `broker_order_id` の観測・store 読み取り失敗を含む)/ `query_failed`。
- 照会失敗は状態を推測しない: 対象特定できる失敗は `query_failure` discrepancy、Broker 側注文の列挙失敗・列挙非対応は run の `broker_listing_error`(「Broker のみの注文なし」ではなく「未確認」)。`has_partial_failures` で query/listing の部分失敗を機械判定できる。
- Broker 側注文の列挙には追加の optional Protocol `broker.broker_interface.OrderListingBroker` を使う(既存 `Broker` の 5 操作は無変更 = 後方互換。FakeBroker が実装)。
- **修復(Issue #104)**: 保存済み run のみを入力とし、attempt を**監査 DB へ claim(owner + lease + generation)してから**再検証する(`client_order_id` 対応、**revision gate** = 観測後のあらゆる変更(same-state 含む)を検出、**Broker 再照会**は `already_applied` 判定前にも必須で 3-way 一致(観測 × 内部 anchored × fresh)を要求、既存 validator 全通過、Broker 参照 ID を失わない)。適用は fence install → `record_order_result(expected_current_state=..., expected_revision=..., repair_fence=...)` の **fencing された原子的 compare-and-set** 1 呼び出しのみで(identity 5 要素 + revision + state がトランザクション内ですべて一致した場合だけ commit)、**APPLIED attempt は commit 前に完全構築**されるため commit 後の例外が結果を偽ることはない。再実行・並行実行しても状態履歴は高々 1 行(history 側も partial UNIQUE で強制)。全 attempt は claim → finalize の 2 段階で `broker_reconciliation_repair_attempts` に確定し、finalize 失敗・crash は pending として残って、**lease 期限後に** `recover_pending_attempts()` が **durable takeover intent** を作って takeover し(cross-DB の各段階で落ちても**同じ identity で再開**)、**history の構造化 `repair_attempt_id` / `repair_generation` 列**(reason 解析ではない)で元 attempt ID のまま確定するか、新 owner として再評価する。takeover 後の旧 worker は Execution commit も finalize もできない(fence / claim CAS が typed に拒否)。`fence_installed` は「過去のある時点で fence がこの identity を指していた」という歴史的事実であり、claim 昇格の許可そのものではない — 昇格時に guard 下で現在の fence を再検証する。`fence_installed` の記録も **Execution DB の commit 済み fence 行を読んで**行うため、fence 設置直後に落ちた worker の続きを、in-memory の値なしに再開できる(逆に、install 後に別 attempt が order を奪った場合は BLOCKED になり、identity が分裂したまま進むことはない)。自動収束できない不整合(fence 先行・identity 不一致・複数 active intent・**terminal intent なのに attempt が pending** 等)は `BLOCKED` として intent 行へ永続化され、呼び出し側へも typed に返る(空 tuple の黙殺をしない。intent 作成競合も原因を再読して正常競合と異常競合に分類する)。
- **position / trade / SL・TP スコープ(Issue #105)**: `include_position_scope=True` の検出のみ・全件 `manual_review`・修復経路なし(repair は order discrepancy しか読まない)。Broker のみの position / trade の自動採用、内部のみ position の自動 close、SL / TP の自動再作成・変更は行わない。手動照合は `python -m execution.reconciliation_runner`(reconcile-only・OANDA Demo 限定 / FakeBroker)。
- 非スコープ: Broker への write 操作、Broker のみの注文・position・trade の自動採用・position 自動 close・SL / TP 再作成・変更、position ドメインへの修復拡張、scheduler 組み込み、**処理中の lease heartbeat**(固定 lease + `broker_timeout < lease_duration` の構築時検証で代替。intent の lease は再開の排他としてのみ CAS で取り直す)、**blocked からの自動復旧**(人手の判断が必要)、intent / fence 行の GC(監査証跡として保持)。

設計の詳細は [docs/architecture/broker_reconciliation.md](../docs/architecture/broker_reconciliation.md) を参照。

## 固定シナリオ試験(Issue #77)

実発注処理は実相場や Broker 障害を待って検証できないため、正常約定だけでなく拒否・部分約定・timeout(結果不明)・DB保存失敗・多重起動競合などを**固定データから決定的に再現**する試験基盤(固定シナリオは Issue #78 / PR #100 の Shadow Mode 系 13 件、Issue #116 の再発行系、Issue #99 のキャンセル系 6 件を含め現在 **48 件**)。Shadow シナリオ(`shadow` / `shadow_concurrent` / `shadow_production` ステップ)も同じ runner が Production API(`ShadowExecutionService` / `run_production_shadow_cycle`)を呼ぶだけであり、runner が Shadow 記録を直接構築・保存しないことは AST 検査で固定される。通常の pytest がモジュール単位の観点を固定するのに対し、固定シナリオは「入力 → Safety Gate → Broker → 永続化」の分岐 1 本を 1 シナリオとしてデータで表現する。**試験対象の判定はすべて本番コード**(`LiveOrderSubmissionService` / `SafetyGate` / `execution_store` / broker の状態機械)であり、runner は wiring・actual 収集・比較のみを行う(`tests/test_scenario_runner.py` の AST 検査が遷移表・validator の import を禁止)。`mark_submitting` / `record_unknown` ステップは store の公開 API による前提状態・観測の注入であり、ユースケースの合成ではない。

**キャンセル固定シナリオは Issue #99 で復帰済み**: Issue #77 / PR #96 レビュー時点では Production キャンセルユースケースが未実装だったため対象外としていたが、`LiveOrderSubmissionService.cancel()`(公認キャンセル経路)の実装に伴い、`cancel` ステップが**その公開 API のみ**を呼ぶ形で復帰した(成功 / Broker 確定拒否 / terminal 拒否 / 重複抑止 / timeout UNKNOWN / DB 保存失敗の 6 件)。runner に試験専用キャンセル経路は存在しない(PR #96 レビューの合成禁止はそのまま)。FakeBroker のキャンセル振る舞い(成功・失敗・timeout・terminal 拒否・呼び出し記録)は `broker/tests/test_fake_broker.py`、Execution Store の CANCELLED 遷移は `tests/test_execution_store.py`、サービス境界の cancel 契約は `tests/test_cancel_submission.py` の通常 pytest が検証する。

### 実行方法

```bash
python -m execution.scenario_runner                       # 全シナリオ
python -m execution.scenario_runner --list                # シナリオ一覧
python -m execution.scenario_runner --scenario-id <id>    # id 指定(複数可)
python -m execution.scenario_runner --scenario-file <path>  # ファイル指定
python -m execution.scenario_runner -v                    # expected/actual と本番ログを表示
python -m execution.scenario_runner --json                # machine-readable JSON 結果
```

- 出力: シナリオごとに `PASS / FAIL / ERROR` + scenario id + description、FAIL 時は不一致フィールドの expected/actual 差分、末尾に総数・PASS/FAIL/ERROR 数・実行時間・失敗シナリオ一覧。
- 終了コード: **0 = 全シナリオ PASS のみ**。FAIL(expected 不一致)または ERROR(未処理例外)が 1 件でもあれば 1、usage・シナリオ定義エラーは 2。
- コンソール encoding 非依存(PR #96 レビュー): 区切り文字は ASCII、`--json` は pure ASCII(`ensure_ascii`)、自由テキストは encode 不能文字をエスケープへ退避する。Windows 既定の cp932 コンソールでも(`PYTHONUTF8` なしで)クラッシュせず、終了コード契約が保たれる(cp932 を再現する pytest と Windows CI ジョブで固定)。この encoding 退避は `main()` 実行中のみで、stdout / stderr の設定は正常終了・usage error・schema error・未処理例外のすべての経路で元へ復元される(import 時には一切変更しない。pytest で固定)。
- CI では pytest スイート(`tests/test_fixed_scenarios.py` がシナリオ id 単位で parametrize)と CLI ステップ(Ubuntu / Windows)の両方で実行される。

### シナリオ定義(schema)

`scenarios/*.json`(1 ファイル = 1 シナリオ、ファイル名順にロード)。schema は `scenario_models.py` が closed-world で検証し、必須フィールド欠落・未知キー・未知 behavior/注文状態/拒否コード・型不一致・重複 scenario id は**ロード全体を失敗させる**(silent skip なし)。価格・数量は Decimal 文字列(float 禁止)。

| キー | 内容 |
|---|---|
| `scenario_id` / `description` | `^[a-z0-9_]+$` の一意 id と説明 |
| `gate` | Safety Gate 側の状態: `kill_switch`、policy 上書き(`max_order_quantity` / `allowed_symbols` / `allowed_fake_targets` / `allowed_shadow_targets` / `max_reference_age_seconds` など。既定: USD_JPY・数量上限10・鮮度30s・接続先 `fake` / `shadow`) |
| `market` | 市場 snapshot: `reference_price` / `bid` / `ask` / `age_seconds`(固定 clock からの経過秒。stale 再現用)/ `market_open` / `tradable` |
| `broker` | FakeBroker 設定: `default_fill_price` / `connection_target` / `scripts`(client_order_id → behavior: `fill_immediately`(`price`・`broker_order_id` 指定可)/ `stay_pending` / `partially_fill` / `partially_fill_then_reissue`(Issue #102: 部分約定 + 残数量 reissue。`reissued_broker_order_id` 指定可)/ `reject`(`reason`・`category` = RejectionCategory 値。Issue #114/#116)/ `timeout` / `fail_communication`)/ `cancel_scripts`(Issue #99: client_order_id → behavior: `fail_cancellation`(確定拒否)/ `timeout`(cancel 結果消失)。未 script の注文はキャンセル成功) |
| `faults` | fault injection: `boundary` = `initial_save` / `mark_submitting` / `record_order_result` / `record_order_state` / `state_history` / `shadow_claim` / `shadow_result_save`(completion)/ `safety_decision_record` + `after_calls`(最初の N 回は成功)または `fail_calls`(最初の N 回だけ失敗。stale claim 回収用) |
| `signals` / `production_config` | `shadow_production` ステップ用: 保存済み Signal fixture(runner が一時 paper-signal DB へ seed し、**Production の `PaperSignalDbSignalProvider` が読む**)と、Production parser が検証する完全明示の実行設定 |
| `steps` | 宣言的ステップ列。`register` / `submit` / `cancel`(Issue #99: **Production の `LiveOrderSubmissionService.cancel()` のみ**を駆動。`at_offset_seconds` でサービス clock を Broker の決定的 tick より後へ移動可能。expect `outcome` = cancelled / refused / broker_refused / error + `refusal_code`(`CancelRefusalCode` 値)/ `state` / `error_type` / `error_code`)/ `record_unknown` / `mark_submitting` / `submit_concurrent` / `register_concurrent` / `shadow`(`dry_run` / `owner_id` / `at_offset_seconds` / `claim_lease_seconds` 可)/ `shadow_concurrent` / `shadow_production`(`signal_id`)/ **Issue #116 再発行系**: `grant_clearance`(`signal_id`。Production の `ReissueClearanceService.observe_signal()` を駆動。expect `outcome` = granted / not_granted / error)・`manual_reissue`・`gate_correction`(request + `client_order_id` + `parent_execution_request_id` + `operator_id` + `reason`。Production の `ReissueService` を駆動。expect `outcome` = registered / refused / error)。shadow 系の `expect` は `outcome` = recorded / duplicate / dry_run / **conflict** / error + `allowed` + `conflict_fields` |
| `expected` | 最終結果の比較: `final_phase` / `final_state` / `state_history`(履歴エントリのオブジェクト列。件数・順序は常に厳密比較。各エントリは `previous_state` / `new_state` 必須 + `reason` / `broker_order_id` の部分比較 — **キー省略 = 比較しない、明示 `null` = NULL であること**の区別あり。`changed_at_utc` の存在と単調性は宣言に関係なく常に検証、動的 timestamp の完全一致比較はしない)/ `broker_submit_calls` / `broker_cancel_calls`(Issue #99: FakeBroker が記録した cancel **試行**回数。成功・拒否・timeout を問わない)/ `submitted_request`(Broker へ渡った request の部分一致)/ `order_rows` / `history_rows` / `safety_decisions` / `last_decision_allowed` / `last_decision_codes` / `broker_order_id` / `filled_quantity` / `average_fill_price` / `fill_prices` / `requested_price` / `reject_reason` / `listed_unknown` / `listed_unresolved` / **Shadow 系(Issue #78)**: `shadow_rows`(completed)/ `shadow_claim_rows` / `shadow_db_created` / `decision_db_created` / `shadow_allowed` / `shadow_codes` / `shadow_intended_order` / `shadow_origin` / `shadow_phase` / `shadow_account_id` / `shadow_safety_decision_id` / **再発行系(Issue #116)**: `chain`(primary signal のチェーン全 attempt を execution_request_id / signal_attempt / submission_phase / order_state で厳密比較)/ `journal_outcomes`(intent ごとの journal outcome。`null` = entry 不在) |

実行ごとに変動する値は比較しない設計: runner は固定 clock(`NOW` = FakeBroker の決定的 clock base)を注入し、`broker_order_id` は比較したいシナリオが script で固定値を指定する。DB 採番値(history_id)は比較対象外。

### fault injection

DB 保存失敗は、シナリオ実行中だけ `execution_store` の対象関数を例外を送出するスタブへ差し替えて再現する(終了時に必ず復元。テスト専用の依存差し替えであり、**本番コードに環境変数ベースの隠し故障モードは存在しない**)。境界は「Execution Request 初期保存」「SUBMITTING 遷移保存」「Broker 受付後の結果保存」「状態履歴保存」を区別し、Broker 受付後の保存失敗が「未送信」や即時再送可能状態に化けないこと(UNKNOWN 記録 + `list_unresolved_submissions()` での可視性 + 再送拒否)をシナリオが固定する。

### 副作用の隔離

各シナリオは専用の一時ディレクトリ内に `orders.sqlite3` / `safety.sqlite3` を作り(パスは明示注入。`EXECUTION_ORDER_DB_PATH` 等の既定パスは参照しない)、Broker は in-memory の FakeBroker のみ。外部 Broker API・Discord・S3・`.env`・state ファイル・ネットワークへの副作用はない(socket 無効化下でも PASS することを pytest が固定)。シナリオは相互に独立で、実行順序に依存しない。

### シナリオの追加方法

1. `scenarios/` に `NN_<scenario_id>.json` を追加する(`scenario_id` はファイル内で宣言。全ファイルで一意)。
2. 上記 schema に従い `steps` と `expected` を書く。分岐の判定を試験側へ複製しない — 期待する状態・回数・コードだけを宣言する。
3. `python -m execution.scenario_runner --scenario-id <id>` で確認する。`tests/test_fixed_scenarios.py` は `scenarios/` を自動で拾う(Issue #77 必須シナリオは id を pin しているため、削除・改名は fail する)。

## 位置づけ(誤解しないこと)

- 注文状態の唯一の正は既存の `broker.OrderState` / `validate_order_state_transition()` / `validate_order_result_update()`(Issue #73 / PR #87)。**本パッケージは注文状態 Enum・遷移表を新設しない。** CREATED / SUBMITTING は注文状態ではなく Execution Request 側の**送信フェーズ**(別フィールド)である。
- Safety Gate は将来の Live Execution 送信経路を安全にする**部品のみ**であり、OANDA Adapter・Live 接続・実注文 runner は**未実装**。reconciliation は Issue #103 の**差分検出**と Issue #104 の**注文状態の安全な修復**(内部 DB のみ・Broker write なし)まで実装済みで、position / SL・TP 照合と定期実行は未実装。`ExecutionMode` に `paper` は存在しない(Paper Execution は Broker 境界を使わず、Safety Gate を通らない)。
- **Paper Signal / Paper Execution は本パッケージを使わない**(`tests/test_package_imports.py` が回帰として固定)。
- UNKNOWN は即時再送可能状態ではない。照会対象として抽出し、後続照会結果の記録によってのみ確定状態へ解決する。state-only で記録できるのは UNKNOWN のみで、他のすべての観測は完全な `OrderResult` を `record_order_result` で記録する(stale snapshot による fill 消失・巻き戻しを DB 側 snapshot 検証で拒否)。

設計の詳細は [docs/architecture/execution_request.md](../docs/architecture/execution_request.md)(ExecutionRequest / 永続化)と [docs/architecture/safety_gate.md](../docs/architecture/safety_gate.md)(Safety Gate)を参照。
