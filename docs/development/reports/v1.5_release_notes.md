## v1.5 に含まれる変更(`v1.4.1` タグ以降)

### Paper Execution(仮想執行)

- **Paper Execution 本体**(Issue #49 設計 / #50・#51 実装。`paper-execution/`): 保存済み Paper Signal を入力に、確定足の時間進行に沿って仮想Entry / 仮想ポジション管理(pending / open / closed / expired / cancelled)/ SL・TP・最大保有時間による Exit 判定 / 仮想損益の記録を行う。仮想レコードのみで Broker API・実注文は含まない。
- **Discord 状態遷移通知**(Issue #83): Position 遷移と同一トランザクションで確定する Transactional Outbox・claim/lease・at-least-once 配送。
- **同時ポジション上限**(Issue #85): `(symbol, timeframe, side)` スコープの active 上限。単一 `BEGIN IMMEDIATE` トランザクションで TOCTOU を構造的に防止。

### Strategy 定義の外部化(Backtest 経路)

- YAML schema / loader / validation / `--strategy-file`・`--strategy` CLI(Issue #52〜#54)。読み込むのは Backtest 経路のみで、Paper Signal / Paper Execution との定義共有は未実装。

### Live Execution 基盤(`broker/` + `execution/`)

- **Broker interface / FakeBroker**(Issue #73): Broker 境界(共通インターフェース・Broker 非依存の共通モデル)と、外部通信を一切行わない決定的テストダブル。接続 identity 契約(Issue #75)、注文列挙 / trade 列挙の optional Protocol(Issue #103 / #105)。
- **Execution Request / 注文状態永続化**(Issue #74): `ExecutionRequest` モデルと注文状態・状態履歴の SQLite 永続化。二重発注防止・idempotency(Issue #76)。schema は v5 まで段階 migration(#104 repair fence / #95・#115 再発行チェーン)。
- **発注前 Safety Gate + 判定監査保存 + 唯一の送信境界**(Issue #75): 許可銘柄・数量・ポジション上限・SL/TP・価格鮮度・spread・kill switch・接続 identity を fail-closed で検証し、`LiveOrderSubmissionService` だけが `Broker.submit_order()` へ到達できる(AST 走査テストで構造的に固定)。
- **固定シナリオ試験**(Issue #77): 正常約定 / 拒否 / 部分約定 / timeout(UNKNOWN)/ DB 保存失敗 / 多重起動競合 / キャンセル / Shadow / 再発行系の分岐を固定データで再現する `python -m execution.scenario_runner`(現在 48 シナリオ)。
- **Shadow Mode**(Issue #78): 実 Signal・実設定・Safety Gate を Production 経路で実行しつつ Broker へは一切送信せず、注文候補と Gate 判定を監査保存(`python -m execution.shadow_runner` / `shadow_report`)。
- **OANDA Demo Adapter**(Issue #79): OANDA v20 REST(fxpractice)と共通モデルの変換のみを担う Demo 専用 Adapter。endpoint allowlist で Demo に固定(Live endpoint は fail-closed 拒否)。secrets 非漏洩・redirect 非追従。Execution 層への組み込み(`BROKER_TYPE_BY_MODE` への `demo` 登録)は未実装。
- **Kill Switch**(Issue #81): SQLite 永続・append-only 遷移履歴の緊急発注停止。DB が読めない間は fail-closed で全新規送信拒否。運用 CLI `python -m execution.kill_switch_cli`(解除は `--confirm-resume` 必須)。
- **Submission / Cancellation Journal**(Issue #93 / #99): Broker 送信・キャンセル試行を Execution Order DB と独立に耐久記録。送信前の Journal 保存失敗は fail-closed(送信されない)。Execution DB 全損時も未解決送信を列挙・再送阻止できる。
- **公認キャンセル経路**(Issue #99): `LiveOrderSubmissionService.cancel()` が唯一のキャンセル境界。Broker 呼び出し前の耐久 claim により二重 cancel を構造的に防止。
- **Order Reissue 系**(Issue #102 / #114 / #95 / #115 / #116 / #117): Broker 側 reissue の状態機械と監査 chain(#102)、Broker 中立の正規化拒否分類 `RejectionCategory`(#114)、再発行チェーンの永続化 = execution store schema v5(#95 設計 / #115 実装)、clearance(観測にもとづく再発行許可。#116)、手動再発行 / 訂正差し替え / 自動再試行(#117。**既定無効** = `max_auto_reissues_per_signal` 0)。
- **Broker reconciliation**(Issue #103〜#105): 内部注文状態と Broker 状態の差分検出(#103。検出専用・注文状態を変更しない)、`auto_repair_candidate` に限定した内部注文状態の安全な修復(#104。Broker への write なし)、position / trade / SL・TP スコープの検出(#105。全件 `manual_review`・修復経路なし)、OANDA Demo 専用の手動 reconciliation CLI `python -m execution.reconciliation_runner`(reconcile-only。submit / cancel / 口座照会を構造的に封じた facade 経由)。scheduler への組み込みは未実装。
- **Live 接続の二重以上のロック**(Issue #82 / PR #128): OANDA Live Adapter(fxtrade endpoint 完全一致のみ・既定値なし・Live 専用環境変数)、`execution/live_lock.py`(唯一の Live 接続 composer)、起動前 preflight CLI `python -m execution.live_startup_cli`。Live 接続の構築には `--execution-mode live` / `ENABLE_LIVE_TRADING=true`(厳密一致)/ Live 専用 credential / Live endpoint / `--confirm-live` / Kill Switch が検証可能かつ OFF / safety config(許可銘柄・数量上限・許可 Live target)の**すべて**が必要で、1つでも欠ければ fail-closed。Demo / Live の credential・endpoint 混在は拒否。起動時 safety summary は account id をマスク表示し、token・endpoint URL を一切出力しない。

## Live 運用の位置づけ(実装済み / Live 接続コード / 運用未解禁の区別)

1. **実装済み機能**: 上記の Broker 境界・Safety Gate・OANDA Demo Adapter・reconciliation・Kill Switch・journal・reissue 系。いずれも fail-closed の検証・監査・安全機構であり、外部通信するのは OANDA Adapter のみ(endpoint allowlist で 1 URL に固定)。
2. **Live 接続コードとして存在するもの**: OANDA Live Adapter・`live_lock.py`・`live_startup_cli.py`・`LiveOrderSubmissionService` の Live 送信境界。**全ロック成立時のみ**構築でき、通常 CI・pytest から Live endpoint への接続テストは存在しない(transport 注入の offline テストのみ)。
3. **Live 運用開始**: **未解禁**。少なくとも以下の事前条件をすべて満たしたうえで、別途運用判断する(Issue #82 の merge だけでは開始しない):
   - FakeBroker 固定シナリオ試験が安定している(`python -m execution.scenario_runner`)
   - Shadow Mode で想定注文を確認済み(`python -m execution.shadow_runner` / shadow report)
   - Demo 口座で継続運転済み
   - Broker reconciliation が稼働している(`python -m execution.reconciliation_runner`)
   - Kill Switch が動作確認済み(enable → 送信拒否 → disable)
   - 発注数量・許可銘柄・リスク上限が `--safety-config` に設定済み

## Breaking Changes / Migration

**既存の運用導線(news-feed-bot / market-watch / paper-signal / backtest)に破壊的変更はない。**

- **Paper Position DB**: schema v4 まで自動 migration(v3 → v4 は `virtual_positions` の transactional rebuild。Issue #85)。dry-run では migration しない。
- **Execution 系 DB**(`execution_orders` / `safety_gate_decisions` / `submission_journal` / `kill_switch` / `broker_reconciliation` / `shadow_results`): いずれも新規追加。closed-world schema 検証・pristine init・段階 migration(execution store は v2 → v3 → v4 → v5)で、不正 schema は DB 無変更で拒否する。**これらを定期的に作成・更新する常駐プロセスは存在しない**(手動 CLI・テストのみ)。
- **新規環境変数**: いずれも既定値または unset で従来動作(`EXECUTION_ORDER_DB_PATH` / `SAFETY_GATE_DECISION_DB_PATH` / `SUBMISSION_JOURNAL_DB_PATH` / `KILL_SWITCH_DB_PATH` / `BROKER_RECONCILIATION_DB_PATH` / `SHADOW_RESULT_DB_PATH` / `PAPER_POSITION_DB_PATH` / `PAPER_EXECUTION_DISCORD_WEBHOOK_URL` / OANDA Demo 用 `OANDA_*` / OANDA Live 用 `OANDA_LIVE_*` / `ENABLE_LIVE_TRADING`)。一覧と契約は [Operations](../../operations/operations.md) を正とする。
- **`ENABLE_LIVE_TRADING` は Demo mode のプロセス環境に設定しない**(設定されていると Demo 起動チェックが fail-closed で拒否する)。

## 既知の制約(Known Limitations)

- **実発注を駆動する定期実行 runner・自動売買は未実装**。Live Execution 基盤は手動 CLI とテストからのみ駆動される。
- **実口座での Live 運用は未解禁**(上記の事前条件と運用判断が必要)。
- `demo` execution mode は定義と validation のみ(`BROKER_TYPE_BY_MODE` へ未登録。OANDA Demo Adapter を使うのは手動 reconciliation CLI と opt-in 実 API テストのみ)。
- reconciliation の scheduler / 常駐 Bot への組み込みは未実装(手動 CLI のみ)。
- 外部 Strategy 定義(YAML)は Backtest 経路のみ。Paper Signal / Paper Execution との共有は将来構想。
- 自動再試行(Issue #117)は既定無効であり、有効化には policy の明示 opt-in が必要。
- Market State / 戦略フィルタのエッジは銘柄固有のまま(v1.4.1 の既知制約を継続)。
