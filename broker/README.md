# broker/

**Live Execution** に向けた Broker 境界(Issue #73)。境界定義(`broker_interface` / `broker_models`)と FakeBroker は**実発注も外部通信も行わない**。HTTP を話すのは OANDA Adapter だけで、いずれも**接続先が endpoint allowlist で 1 URL に固定**されている: Demo Adapter(Issue #79)は fxpractice endpoint のみ、Live Adapter(Issue #82)は fxtrade endpoint のみを受け付け、互いの endpoint は構築時に fail-closed で拒否される。

Live Adapter は**ロックが揃わないと存在できない**(Issue #82): Live 専用 endpoint + Live 専用 credential + `ENABLE_LIVE_TRADING=true` + 明示的な `--confirm-live` が構築時の前提条件であり、加えて Execution 層の composer(`execution/live_lock.py`)が Kill Switch と safety policy を検証する。

明示的な Python package。リポジトリルートから import する:

```python
from broker.broker_interface import Broker
from broker.broker_models import OrderRequest, OrderResult
from broker.fake_broker import FakeBroker
from broker.oanda_demo_adapter import OandaDemoAdapter, OandaDemoConfig
from broker.oanda_live_adapter import LiveActivation, OandaLiveAdapter, OandaLiveConfig
```

## 位置づけ(誤解しないこと)

- Broker interface / FakeBroker は**将来の Live Execution 用の基盤**であり、FakeBroker が存在しても **Live Execution が実装済みになったわけではない**。
- **Paper Execution(`paper-execution/`)は従来どおり Broker 非依存の仮想執行**であり、このパッケージを使わない。
- OANDA **Demo** Adapter は Issue #79 で実装済み(Demo 口座での注文ライフサイクル検証用)。ただし **Execution 層への組み込みは未実装**: `execution.safety_gate.BROKER_TYPE_BY_MODE` に `demo` は未登録のままであり、`BrokerConnection` / `LiveOrderSubmissionService` から Demo Adapter を使うことはまだできない(表現不能による fail-closed を維持。登録は Execution 統合の別 Issue で行う)。
- OANDA **Live** Adapter は Issue #82 で実装済みで、`BROKER_TYPE_BY_MODE` に `live` として登録されている。**これは「Live 運用を開始してよい」という意味ではない**: 登録の効果は「FakeBroker は `live` を名乗れず、Live Adapter は `live` 以外を名乗れない」ことだけであり、Live Adapter の instance は全ロックが揃わないと生成できない。**定期実行する Live Execution runner は引き続き未実装**であり、Live 運用開始の事前条件は [運用ドキュメント](../docs/operations/operations.md) の「Live 運用開始の事前条件」を参照。
- 発注前の Safety Gate は Issue #75 で `execution/` に実装済みだが、Broker 実装から独立した検証部品である([Safety Gate 設計](../docs/architecture/safety_gate.md))。
- Issue #75 で本パッケージに追加されたのは**接続 identity の契約のみ**: `broker_models.BrokerConnectionIdentity` と、各 Broker 実装が自身の構築時接続 config から不変の identity を自己申告する `connection_identity()`(FakeBroker は mode `"fake"` 固定 + 構築時 `connection_target`)。これは Issue #73 の 5 操作 Protocol とは別の契約であり、execution 層の型付き `BrokerConnection` が mode / 接続先を **Broker 実体から導出**するために用いる。将来の Adapter も自身の実接続設定から identity を返す義務を負う。
- `runtime_checkable` Protocol の `isinstance()` は属性の存在確認のみ(シグネチャ・型の適合は保証しない)。本リポジトリは静的型検査(mypy / pyright)を実行しておらず、シグネチャ適合を保証する仕組みはない。`tests/` の振る舞いテストが確認するのは FakeBroker の挙動のみで、将来の Adapter は自前のテストで適合を確認する。

設計の詳細は [docs/architecture/broker_interface.md](../docs/architecture/broker_interface.md) を参照。
